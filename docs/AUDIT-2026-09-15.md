## D1. Fresh checkout was not self-contained — FIXED

The repository now commits the official Gradle Wrapper and pins the Gradle distribution SHA-256. CI validates the wrapper JAR checksum and distribution configuration before invoking the build. CI and documentation use `./gradlew`, not a system Gradle installation.

Regression gate:
- `.github/workflows/android-ci.yml` — **Verify committed Gradle Wrapper integrity**, **Verify clean-checkout toolchain**, `./gradlew test`, `./gradlew lint`, `./gradlew assembleDebug`.

## D2. Two workers could collect the same source concurrently — FIXED

Collection ownership is now a persisted expiring lease acquired by an atomic SQL compare-and-set. Only the lease owner performs network discovery. Expired leases can be reclaimed. The claim operation re-checks both lease availability and the due schedule atomically, so a worker holding a stale in-memory due list cannot re-claim a Source after a newer run has already scheduled it into the future. Lease release is token-guarded so a stale owner cannot clear a replacement lease.

Regression tests:
- `CollectionHardeningIntegrationTest.concurrentCollectionRunsClaimOnceReportAlreadyClaimedAndFetchOnce`
- `CollectionHardeningIntegrationTest.expiredLeaseCanBeClaimedByNextRunWithoutRelease`
- `CollectionLeaseDueGuardIntegrationTest.staleDueSnapshotCannotClaimAfterNewerRunSchedulesSourceInFuture`
- `CollectionLeaseReleaseIntegrationTest.staleOwnerReleaseCannotClearReplacementLease`

## D3. Collection commit was non-atomic and stale runs could overwrite newer state — FIXED

`commitSuccess()` and `commitFailure()` execute in Room transactions. Commit ownership is guarded by `sourceId + runToken + settingsRevision + unexpired lease`. A stale/expired run returns `CollectionCommitOutcome.STALE` and cannot write discovery sightings, cursor, schedule, diagnostics, or Source runtime state.

Regression tests:
- `CollectionHardeningIntegrationTest.staleRunCannotOverwriteNewerCommittedState`
- `CollectionHardeningIntegrationTest.expiredLeaseCannotCommitEvenIfNoReplacementClaimedIt`
- `CollectionHardeningIntegrationTest.commitSuccessRollsBackAllRowsWhenMiddleWriteFails`

## D4. Runtime scheduling updates used stale full Source upserts — FIXED

User-owned settings are updated only through `SourceDao.updateUserSettings()` / `saveUserSource()`, which increments `settingsRevision`. Scheduler/runtime updates use addressed SQL (`SourceScheduleDao.markDue`, collection finish operations) and do not rewrite URL, name, enabled state, poll policy, adapter type, or adapter configuration. An in-flight collector whose Source settings changed is made stale and rejected at commit.

Regression test:
- `CollectionHardeningIntegrationTest.userSourceEditsInvalidateInFlightCollectorWithoutBeingReverted`

## D5. Repeat discovery could overwrite newer ingestion state — FIXED

Collection sightings use insert-if-absent plus targeted metadata updates. Scheduler writes do not touch ingestion-owned status, content hash, retry attempts, next processing time, or processing error. `discoveredAt` is the immutable first-observation time; `lastSeenAt` is refreshed on repeat sightings.

Regression test:
- `CollectionHardeningIntegrationTest.repeatedSightingPreservesNewerIngestionStateAndFirstDiscoveryTime`

## D6. Failure isolation and interruption recovery — PARTIALLY FIXED

Collection catches ordinary `Exception` values for source-local adapter failures rather than arbitrary `Throwable`, and `CancellationException` is always rethrown. Collection cancellation releases the owned lease best-effort in `NonCancellable` context and is not recorded as a source failure.

A holistic review found a second interruption window in ingestion: an article could already be persisted as `FETCHED` but the process could stop before the terminal Inbox/Knowledge transaction marked it `PROCESSED`. Because the ready query formerly selected only `DISCOVERED` and `FAILED`, such a row could be stranded indefinitely. `FETCHED` is now an explicit recoverable queue state and is selected again after restart; terminal `PROCESSED`/`SKIPPED` states remain excluded.

A shared storage failure in claim/commit is deliberately **not** converted into a per-source failure: it escapes the orchestrator and is handled by `CollectionWorker` as an infrastructure failure with bounded WorkManager retry. This avoids falsely recording a broken database/storage layer as a remote source failure. Consequently D6 remains partially fixed as originally classified; storage availability is intentionally a run-level failure domain.

Regression tests:
- `CollectionRetrySemanticsTest.cancellationReleasesLeaseAndIsNotRecordedAsSourceFailure`
- `IngestionCrashRecoveryIntegrationTest.fetchedStateIsRecoverableAfterInterruptedIngestion`
- WorkManager infrastructure retry behavior remains an Android integration concern.

## D7. Provenance could be lost or rewritten by later Source lifecycle changes — FIXED

Saved `document_provenance` stores immutable snapshots of Source name, URL, and type and references Source with `ON DELETE RESTRICT`. A holistic review found that the Inbox path still took those snapshots too late: `InboxService.save()` looked up the then-current Source, so a rename/URL/type change between ingestion and Save could rewrite historical provenance.

`InboxOrigin` now captures Source name/URL/type at ingestion time. The snapshot is persisted in `inbox_origins` and copied verbatim into `document_provenance` on Save; Save no longer reads current Source metadata. Pending Inbox provenance also references Source with `ON DELETE RESTRICT`, so an accidental hard delete cannot silently erase an origin before the user saves or discards the item. Normal Source edits, archive/disable operations, and later renames do not alter the snapshot.

Migration 3→4 rebuilds and backfills both pending Inbox provenance and saved Document provenance from the Source state available at migration time. Seen history remains protected with `RESTRICT` as well.

Regression tests:
- `InboxServiceTest.save preserves every ingestion-time origin snapshot and creates saved fingerprints`
- `InboxProvenancePersistenceTest.sourceEditsAfterInboxAttachmentDoNotRewriteOriginSnapshot`
- `InboxOriginMigrationTest.migration3To4BackfillsInboxSourceSnapshotAndRestrictsSourceDelete`
- `CollectionHardeningIntegrationTest.archivedSourceDoesNotChangeSavedProvenanceSnapshot`
- `MigrationHardeningTest.migration3To4PreservesOperationalInboxKnowledgeAndProvenanceData`
- `MigrationHardeningTest.migration1To2To3To4PreservesDataAcrossFullSupportedChain`

## D8. HTTP body was unbounded and Call was not coroutine-cancellable — FIXED

`OkHttpTransport` uses `suspendCancellableCoroutine`; coroutine cancellation calls `OkHttp Call.cancel()`. Response reading is bounded both by advertised `Content-Length` and a streaming byte counter for chunked/unknown-length responses. Feed and article acquisition use separate bounded limits (2 MiB and 5 MiB respectively). Dispatcher limits also cap global and per-host concurrent requests.

The cancellation regression test itself is fail-fast and starts the HTTP coroutine before any blocking MockWebServer request observation, preventing the test harness from deadlocking while still verifying the real OkHttp cancellation path.

Regression tests:
- `OkHttpTransportTest.cancellingCoroutineCancelsOkHttpCallAndStopsBodyRead`
- `OkHttpTransportTest.contentLengthAboveLimitFailsBeforeBufferingBody`
- `OkHttpTransportTest.chunkedBodyWithoutContentLengthIsLimitedWhileStreaming`
- `OkHttpTransportTest.responseExactlyAtLimitSucceeds`
- `OkHttpTransportTest.responseBelowLimitSucceeds`
- `ResponseLimitPolicyTest.feedAndArticleUseDistinctBoundedResponseLimits`

## D9. Feed validators survived a fresh 200 that omitted them — FIXED

A 304 response preserves prior ETag/Last-Modified when the server omits them. A fresh successful 200 replaces the validator set; absent validators explicitly clear stale values.

## D10. HTTP retry classification was incomplete — FIXED

Feed and article acquisition distinguish permanent client failures from transient HTTP/transport failures. 401/403/404 do not enter aggressive exponential retry. 408/425/429/5xx and transport timeouts use retry policy. `Retry-After` accepts seconds and RFC-1123 HTTP dates; invalid/past values fall back to local policy. A server delay is a minimum: it wins only when larger than local backoff and never shortens the local safety delay.
