## D6 / R1–R3. Durable article ownership and interruption recovery — FIXED

Stage 2 closes the article-processing ownership gap rather than relying on an in-memory ready list. Every runtime processing attempt first acquires persisted `processingLeaseToken + processingLeaseExpiresAtEpochMillis` ownership. Raw persistence, `FETCHED`, retry, skip and terminal success mutations all re-check the same token and unexpired lease. An expired or replaced owner becomes stale and cannot overwrite a newer attempt.

A successful HTTP response is durably persisted before extraction/finalization. The v5 `raw_contents` row stores the response bytes as BLOB plus content type, resolved URL, fetch time, HTTP status and expiry. If the process stops after fetch, reopening the database can reuse valid raw bytes without another HTTP request. Expired raw is refetched and deterministically replaced inside the owner transaction using explicit update-existing / insert-if-absent semantics. A failed terminal transaction retains the recoverable raw/FETCHED state and can resume after reopen.

Shared infrastructure failures remain a run-level failure domain rather than being misclassified as remote article errors. If such an exception escapes after article ownership was acquired, the pipeline best-effort releases its lease in `NonCancellable` context before propagating the original failure to WorkManager. If storage is itself unavailable, lease expiry remains the durable fallback. Cancellation follows the same ownership-safe release rule and is rethrown.

## R3–R4. Atomic Inbox/Knowledge lifecycle — FIXED

Runtime article success no longer performs a sequence of independently visible repository writes. Under one Room transaction it re-checks ownership, deduplicates against saved Documents / dismissed fingerprints / pending Inbox, attaches or creates provenance, marks the discovery `PROCESSED`, clears the processing lease, and deletes temporary raw content. A transaction failure rolls back the whole boundary.

User actions use a second transactional boundary. Save reads the current Inbox item and all current origins after the transaction begins, resolves/creates the saved Document and version, writes every provenance snapshot and seen fingerprint, finishes the corresponding discoveries, removes raw data and consumes the Inbox row atomically. Reject and Read-and-Discard perform the equivalent atomic dismissal boundary. Save-vs-reject has exactly one committed winner.

A late article finalization cannot silently lose provenance. If Save committed first, the finalizer observes the saved Document and attaches the late origin directly to it. If Reject/Read-and-Discard committed first, the finalizer observes the dismissal fingerprint and carries that disposition forward instead of recreating Inbox.

## R5 / R7. Bounded passes and WorkManager continuation — FIXED

A collection pass has a shared time budget and bounded item counts. Source discovery stops at its per-pass cap/deadline. Article processing stops at its own cap/deadline. Reaching a count cap is not automatically treated as backlog: each side determines whether eligible persisted work actually remains before setting `budgetExhausted`.

`CollectionWorker` publishes combined source/article diagnostics. Shared-infrastructure exceptions use bounded WorkManager retry rather than being recorded as Source/article failures. A pass that leaves persisted work because its budget was exhausted returns WorkManager retry so continuation itself is durable rather than an in-process loop. Periodic work requires network plus battery-not-low; immediate work requires network; both are registered as unique work and their replacement/cancellation semantics are tested.

Regression evidence:
- scheduler-core budget tests in `CollectionOrchestratorTest`
- ingestion budget tests in `IngestionPipelineTest`
- `CollectionWorkSchedulerTest.periodicWorkRequiresNetworkAndHealthyBattery`
- `CollectionWorkSchedulerTest.immediateWorkRequiresNetworkButDoesNotRequireHealthyBattery`
- `CollectionWorkSchedulerTest.ensurePeriodicRegistersOneUniquePeriodicWork`
- `CollectionWorkSchedulerTest.runNowReplacesPreviousImmediateWork`
- `CollectionWorkSchedulerTest.cancelImmediateCancelsCurrentUniqueWork`
- `CollectionWorkSchedulerTest.sharedInfrastructureFailureRequestsWorkManagerRetry`
- `CollectionWorkSchedulerTest.exhaustedSharedPassBudgetRequestsPersistedRetry`

A non-integrity refinement remains for a future scheduler pass: repeated `Result.retry()` continuations share WorkManager exponential-backoff semantics, so a very large sustained backlog can progressively increase the delay between bounded passes. No work is lost, but a dedicated continuation-work policy could improve drain latency without weakening resource bounds.
