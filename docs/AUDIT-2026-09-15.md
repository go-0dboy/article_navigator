# Engineering audit — 2026-09-15

Scope: current `feat/phase4-ingestion-inbox` state, reviewed before hardening. This document intentionally distinguishes confirmed defects from architecture risks, planned-but-missing functionality, and optimizations that require measurement.

## Confirmed defects

### D1. Fresh checkout is not self-contained

Files: `docs/BUILDING.md`, `.github/workflows/android-ci.yml`, repository root.

Scenario: clone the repository on a machine without a matching system Gradle installation.

Impact: there is no committed Gradle Wrapper, so the documented build cannot start with `./gradlew`; wrapper/distribution integrity is not enforced by the repository itself. `BUILDING.md` also describes compile/target SDK 36 while the current Android app compiles with API 37.

### D2. Two workers can collect the same source concurrently

Files: `scheduler/core/.../CollectionOrchestrator.kt`, `storage/database/.../Daos.kt`, `scheduler/android/.../CollectionWork.kt`.

Scenario: periodic WorkManager work and immediate/manual work overlap. Both call `findDue()` before either has changed source state.

Impact: duplicate HTTP requests, competing cursor/schedule updates, stale diagnostics, and races with ingestion.

### D3. Collection commit is not atomic and has no stale-run guard

Files: `scheduler/core/.../CollectionOrchestrator.kt`, `core/data/.../Repositories.kt`, `storage/database/.../RoomRepositories.kt`.

Scenario: network discovery succeeds, then the process is interrupted while discovered items, cursor, next schedule and diagnostics are being saved; or a slower older run finishes after a newer run.

Impact: partial state can be committed and an old run can overwrite newer cursor/schedule/diagnostic state.

### D4. Runtime scheduling updates use full Source upsert

Files: `scheduler/core/.../CollectionOrchestrator.kt`, `app/.../AppContainer.kt`, `storage/database/.../RoomRepositories.kt`.

Scenario: the user changes `enabled`, URL, polling interval or another source setting while a request is in flight. The collector later executes `upsert(source.copy(...))` from the stale snapshot it started with.

Impact: user settings can be silently reverted.

### D5. Repeat discovery can overwrite newer processing state through a read/merge/full-upsert race

Files: `scheduler/core/.../CollectionOrchestrator.kt`, `storage/database/.../Daos.kt`.

Scenario: scheduler reads an existing discovered item, ingestion changes its status/content hash/relevance before scheduler writes the merged copy.

Impact: the stale full upsert can restore old internal processing state. The current merge helper preserves values from the object it read, but does not protect against concurrent updates after that read. First discovery time is also not modeled separately from later sightings.

### D6. Source isolation is incomplete and Throwable is too broad

File: `scheduler/core/.../CollectionOrchestrator.kt`.

Scenario: `stateRepository.load()` fails before the guarded network block, or persistence in `fail()` throws. Also, arbitrary `Throwable` values inside collection are treated as ordinary source failures except cancellation.

Impact: one storage failure can cancel the entire coroutine scope; fatal/runtime infrastructure failures can be misclassified as source errors.

### D7. Saved provenance is physically vulnerable to source deletion

File: `storage/database/.../Entities.kt`; ADR `0006-source-lifecycle-preserves-provenance.md`.

Scenario: a Source row is physically deleted by migration, maintenance code or a future repository API.

Impact: `document_provenance` currently has `ON DELETE CASCADE`, so a saved document can lose the answer to “where did I find this?”. This contradicts the accepted archive-source policy.

### D8. HTTP response body is read without a hard byte limit and synchronous Call is not coroutine-cancellable

File: `core/network/.../HttpTransport.kt`.

Scenario: a server sends a very large/chunked body without `Content-Length`, a response stalls, or the coroutine is cancelled while OkHttp is blocked.

Impact: excessive memory use, long-running background work, and delayed cancellation. `response.body.bytes()` buffers the entire body.

### D9. Feed validators survive a normal 200 response that omits them

File: `collector/rss/.../RssAtomSourceAdapter.kt`.

Scenario: the server previously supplied ETag/Last-Modified, then responds `200 OK` without one or both validators.

Impact: the old validator is retained and sent later even though the successful 200 response no longer validated it. `304` handling should preserve prior validators when the server omits them; `200` should replace the validator set with the response values.

### D10. HTTP retry classification is incomplete

Files: `collector/rss/.../RssAtomSourceAdapter.kt`, `scheduler/core/.../CollectionOrchestrator.kt`, `pipeline/.../IngestionPipeline.kt`.

Scenario: feed or article endpoint returns 429/503 with `Retry-After`, or a permanent 4xx.

Impact: the scheduler does not currently coordinate retry timing with HTTP semantics; server-requested backoff is ignored at source-collection level.

### D11. UI polls storage every two seconds

File: `app/.../MainActivity.kt`.

Scenario: app stays open.

Impact: repeated database reads and recomposition regardless of whether data changed. This should be replaced by lifecycle-aware Flow/ViewModel observation.

## Architecture risks

- `Source` mixes user configuration and operational schedule fields. Even after targeted update methods are added, keeping those concerns in one row requires explicit version/lease semantics.
- `findDue()` returns the full due set and the orchestrator creates one coroutine per source before the semaphore limits active work. This scales poorly for large source sets.
- There is no per-host request budget yet; global parallelism alone can hit one host too aggressively.
- Exact `contentHash` merging is currently an implicit identity policy. It may be useful for byte/text-identical republishing, but must be documented and must not be extended to fuzzy/text-similarity merging without an explicit product policy.
- The current source-archive ADR relies on application discipline. Database constraints should also prevent provenance loss.
- `Document.canonicalUrl` is unique, while update/version behavior for changed content at the same URL is not yet defined.
- `SeenFingerprint` is source-scoped. Rejected content found via another source may legitimately reappear; the product policy should state whether that is desired.
- Background collection can miss entries that appear and disappear from an RSS feed between Android wake-ups. No phone-only implementation can guarantee otherwise.

## Not yet implemented functionality

These are planned or newly reprioritized capabilities, not regressions:

- durable Knowledge Library reader with provenance UI;
- offline FTS search over saved title/body/provenance/notes;
- export/import and backup/restore;
- Android share-target for saving a URL directly;
- explicit content-completeness state (full text vs RSS excerpt/link-only);
- document update/version policy for changed content at an existing URL;
- Inbox/raw-data size limits, retention and low-storage behavior;
- notes/tags;
- semantic/vector search;
- generated answers/summaries;
- advanced interest learning;
- Android Worker integration tests;
- lifecycle-aware ViewModel/Flow UI state.

## Optimizations that require measurement

Do not implement these only on intuition:

- additional SQL indexes beyond those justified by actual queries and `EXPLAIN QUERY PLAN`;
- batch sizes for discovery inserts and due-source selection;
- optimal collection concurrency and per-host concurrency;
- chunk/vector layout for semantic search;
- database compaction policy;
- parser/embedding caching.

Before optimizing, record device model, Android version, number/size of sources and documents, collection duration, peak memory, DB growth, battery impact and search latency.

## Hardening order

1. Reproducible build and audit baseline.
2. Data preservation and source collection lease/atomic commit.
3. Network limits, cancellation, validators and retry semantics.
4. Android Worker integration tests and scheduling behavior.
5. User value path: RSS/Atom or Share URL -> acquire material -> read -> save -> offline exact search -> provenance -> export/restore.
6. Only then semantic search, answer generation and sophisticated interest learning.
